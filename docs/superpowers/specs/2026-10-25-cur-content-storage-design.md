## Goal

Several v1 units store files people upload: `cur-profile-photo`, `cur-resources-library`,
`msg-attachments`, and `adm-teacher-application` if it stays in v1. Today a file has
nowhere durable to go:

- `MEDIA_ROOT` is `kaleem/media` inside the container.
- There is no `STORAGES` setting and no media volume.
- `ship.sh` removes the old colour's containers on every deploy, so anything written there
  is lost at the next colour flip.

This unit gives `content` a durable, private place for files and a small public API to
use it:

- `UserUpload`, the record of one stored file;
- `upload_user_file`, which stores a file and records it;
- `download_url`, which returns a short-lived signed URL.

Production and staging use a private AWS S3 bucket in the EU (`dec-cur-storage-provider`,
owner's choice 2026-10-25). Local development and CI use the filesystem. `content` joins
the personal-data registry (ADR-0048).

**Done** means a file written before a real staging colour flip can still be read after
it.

Base at writing: backend `origin/main` `a7b7c97`, infra `ab91adc`, meta `master`
`7d77ded`. Its dependencies have merged: `plat-module-scaffolds` (the empty `content`
app) and `plat-dsar-registry` (`kaleem.platform.personal_data`).

## Decisions taken in this spec

The ADR for this unit ("storage and file serving") records items 1 to 4.

1. **The server stores and signs. The browser never talks to the bucket to write.**
   - Bytes reach the bucket through the API. A consumer's endpoint passes the file to
     `upload_user_file`.
   - This keeps `cur-upload-safety`'s checks (sniffed type, size caps, image re-encode) on
     the only path into the bucket.
   - It also means the bucket needs no CORS rule and the dashboard's `FileUpload` stays
     as it is, posting through `src/lib/api.ts`.
2. **Files are read through signed URLs on the provider's own domain.**
   - A URL is `https://<bucket>.s3.<region>.amazonaws.com/<key>?X-Amz-...` and expires
     after **300 seconds**.
   - The file is never on a `kaleem.academy` host, so a stored file cannot run script with
     access to kaleem's cookies.
   - Every URL is signed with a `response-content-disposition: attachment` that carries
     the original name, encoded per RFC 5987 so Arabic names survive. It is also signed
     with the stored `response-content-type`. A navigation therefore downloads the file
     and does not render it. `<img src>` ignores the disposition, so photos still display.
   - The local filesystem backend returns a plain `/media/<key>` URL, which is served
     only when `DEBUG` is on, as it is today.
3. **`content` never decides who may read a file.**
   - `download_url` and `get_upload` trust their caller.
   - Each consumer checks access first: chat membership, the teaching link and so on.
     Each consumer's own spec states its check.
   - This matches ADR-0049: `content` is a leaf and imports nothing beyond `identity`.
4. **One storage alias, `uploads`, read at call time.**
   - `STORAGES["uploads"]` is the filesystem in `base.py`, so local, test and CI use it.
     `production.py` points the alias at S3.
   - The model keeps the object key in a `CharField`, not a `FileField`. A `FileField`
     resolves its storage once at import, and `override_settings` could then not move
     tests onto a temporary directory.
   - `STORAGES["default"]` and `["staticfiles"]` keep today's backends. Nothing personal
     may use `default`.
5. **Object keys are random and say nothing.**
   - A key is `u/<uuid4 hex>`, so no user id, filename or kind appears in a key, a URL
     path or a provider log.
   - Keys are generated by the server, so a collision is not a practical case. The
     backend runs with `file_overwrite=True`, which skips the existence check. That check
     would otherwise need the list permission (item 7).
6. **One bucket and one IAM user per environment.** Staging and production share a
   server (owner decision 2026-10-25), and each has its own bucket and its own key in its
   own `.env.production`. Neither key can reach the other bucket. Separate buckets are
   chosen over prefixes so that versioning, lifecycle and access are separate too.
7. **Least privilege, stated as a control.**
   - The application key may put, get and delete objects and abort a multipart upload in
     its own bucket only.
   - It may not list the bucket, read or delete old versions, or change any bucket
     setting.
   - Removing an old version is left to the lifecycle rule, so a leaked application key
     cannot permanently destroy stored files.
8. **Deletion is row first, object after commit.**
   - `delete_upload` and the erase hook delete the row. They delete the object in
     `transaction.on_commit`, so a rolled-back request never loses a file that its row
     still points to.
   - `upload_user_file` writes the object, then inserts the row. If the insert raises, it
     deletes the object before re-raising.
   - One case is left: the caller's outer transaction rolls back after both steps
     succeeded. That leaves an object with no row. Its key is random and never signed,
     so nothing can reach it. Sweeping these objects is `cur-content-retention`'s job,
     together with the list permission it will need (`dec-cur-retention`: orphans after
     24 hours).
9. **Kinds are a code enum, not database choices.**
   - `UploadKind` is a `StrEnum` with `profile_photo`, `resource` and
     `message_attachment`, one for each unconditional consumer.
   - `kind` is a plain `CharField(32)`. The service refuses a value outside the enum with
     a `ValueError`, because that is a programming error, not a user error.
   - Adding a kind is one line of code and needs no migration, so parallel consumer
     units never collide on `content`'s migrations.

## User flow

No user sees a change. This unit has no endpoint and no page. Its consumers are the
first user-facing flows.

The operator flow is the staging check below. It uses the new management command
`check_upload_storage`:

- **Default mode** writes a random canary object under `canary/` and reads it back
  through the storage. When the URL is absolute `https`, it also fetches the signed URL
  and compares the bytes. Then it deletes the object. Any failure exits non-zero and
  names the step that failed (write, read, signed-URL fetch, delete).
- **`--keep`** leaves the canary in place and prints its key.
- **`--existing <key>`** reads, fetches and deletes a canary written earlier.

Failure cases inside the services:

- `get_upload`, `download_url` or `delete_upload` with an unknown id raises
  `NotFoundError(pgettext_lazy("error resource", "File"), id)`. Its code is `not_found`
  and it has an Arabic catalog entry. `delete_upload` of an id that was already deleted
  is the same not-found, never a silent success.
- Production settings with any of the four variables missing fail at import
  (`ImproperlyConfigured`). The new colour never becomes healthy, and `ship.sh` rolls
  the deploy back. That is why `hg-vps-env` must come before the merge.

## Data model delta

One new table, `content_userupload`, in migration `content/0001_initial`:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | BigAutoField | |
| `owner` | FK `AUTH_USER_MODEL`, `on_delete=PROTECT`, `related_name="+"` | `PROTECT` means a row (and its object) goes only through `delete_upload` or the erase hook, never as a silent cascade that leaves the object behind |
| `kind` | CharField(32) | an `UploadKind` value |
| `key` | CharField(64), unique | `u/<uuid4 hex>` |
| `original_name` | CharField(255) | as the uploader named the file, for the download name |
| `content_type` | CharField(127) | as the caller passes it. `cur-upload-safety` supplies the sniffed type |
| `size` | PositiveBigIntegerField | bytes written |
| `created_at` | DateTimeField, `auto_now_add` | |

Index on `owner`. The table is purely additive (expand only), so the previous release
ignores it during the blue-green window.

```
identity.User 1 ──< content.UserUpload ──(key)──> object in STORAGES["uploads"]
```

## API delta

No HTTP endpoint. The new public Python API is in `kaleem/content/services.py`:

```python
@dataclass(frozen=True)
class UploadInfo:
    id: int
    owner_id: int
    kind: str
    original_name: str
    content_type: str
    size: int
    created_at: datetime

def upload_user_file(*, owner, kind: str, file: File, original_name: str,
                     content_type: str) -> UploadInfo: ...
def get_upload(upload_id: int) -> UploadInfo: ...
def download_url(upload_id: int) -> str: ...   # signed, 300 s, attachment disposition
def delete_upload(upload_id: int) -> None: ...  # row now, object on commit
```

Other modules call only these. They never import `content.models` (import-linter,
ADR-0049).

**Settings** (backend):

- `base.py` defines `STORAGES` with three entries:
  - `default`: `FileSystemStorage`, unchanged.
  - `staticfiles`: `StaticFilesStorage`, unchanged.
  - `uploads`: `kaleem.content.storage.LocalUploadsStorage`, a `FileSystemStorage` at
    `MEDIA_ROOT` whose `url()` accepts and ignores the signing parameters.
- `production.py` replaces `uploads` with `storages.backends.s3.S3Storage` and these
  options:
  - `bucket_name`, `region_name`, `access_key` and `secret_key`, read from the
    environment as below;
  - `signature_version="s3v4"` and `addressing_style="virtual"`;
  - `querystring_auth=True` and `querystring_expire=300`;
  - `default_acl=None` and `file_overwrite=True`.

  A probe on 2026-10-25 with django-storages 1.14.6 and boto3 1.43 signed such a URL
  offline. The URL used the regional virtual host and carried `X-Amz-Expires=300` and
  both `response-*` parameters.

**Environment variable names**, read by `production.py` only. Each environment's
`.env.production` holds its own values. Values never appear in the repo, in a chat or in
a PR.

| Name | Meaning |
| --- | --- |
| `DJANGO_UPLOADS_BUCKET` | that environment's bucket name |
| `DJANGO_UPLOADS_REGION` | the bucket's region, e.g. `eu-central-1` |
| `DJANGO_UPLOADS_ACCESS_KEY_ID` | that environment's IAM user access key id |
| `DJANGO_UPLOADS_SECRET_ACCESS_KEY` | its secret |

The names are deliberately not the SDK's standard `AWS_*` names. boto3's default
credential chain therefore never picks the key up in code that did not ask for it, and
the SES SMTP credentials stay separate. Every backend container (both colours' Django
and Celery, `flower` and `signaling`) already reads `.env.production`, so
`docker-compose.production.yml` does not change. `infra/.env.production.example` gains
the four names with placeholder values.

**Dependency**: `django-storages[s3]>=1.14,<2.0` in `requirements/base.txt` (boto3 comes
with it). It has an upper bound, for the same reason as `stripe`. The `Dockerfile`'s
build-only `collectstatic` env gains build-only values for the four names.

## Owner setup (hg-cur-storage-credentials): exact bucket and IAM settings

Do this once per environment (staging, then production), in the AWS account that already
has the SES setup.

**Bucket** (region `eu-central-1` or another EU region; the name is the owner's choice):

- **Block Public Access:** all four settings on. Also turn them on at account level.
- **Object Ownership:** Bucket owner enforced (ACLs disabled).
- **Default encryption:** SSE-S3 (AES-256). SSE-KMS is not used: it would add KMS
  permissions and per-request cost for no gain here.
- **Versioning:** enabled.
- **Lifecycle rule** (applies to the whole bucket):
  - non-current versions expire **30 days** after they become non-current;
  - expired object delete markers are removed;
  - incomplete multipart uploads are aborted after **1 day**.

  This is the "versions expire within 30 days" half of `dec-cur-retention`. The offsite
  copy and the restore drill are `cur-media-backup`'s.
- **CORS:** none. Uploads go through the API (decision 1). Downloads are navigations or
  `<img>`, and neither needs CORS. A later unit that reads files with `fetch()` adds a
  rule in its own spec.
- **Bucket policy:** deny any request that is not over TLS.

  ```json
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::<BUCKET>", "arn:aws:s3:::<BUCKET>/*"],
      "Condition": {"Bool": {"aws:SecureTransport": "false"}}
    }]
  }
  ```
- Off: static website hosting, Object Lock, access points, Transfer Acceleration.

**IAM user**: one per environment, programmatic access only (no console password). It
has one inline policy and nothing else:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "KaleemUploadsObjectsOnly",
    "Effect": "Allow",
    "Action": [
      "s3:PutObject",
      "s3:GetObject",
      "s3:DeleteObject",
      "s3:AbortMultipartUpload"
    ],
    "Resource": "arn:aws:s3:::<BUCKET>/*"
  }]
}
```

The policy has no `s3:ListBucket`, no `*Version*` action and no bucket-level action
(decision 7).

Then the conductor sets the four variables in that environment's `.env.production` over
`ssh kaleem` (`hg-vps-env`) before the merge that reads them.

**Vendor DPA (hg-vendor-dpa):** recorded as resolved. AWS's GDPR Data Processing Addendum
is incorporated in the AWS Service Terms, so no separate signature is needed. The
sub-processor is AWS (Amazon S3, in the chosen EU region), for stored user files.
`lb-gdpr-governance-docs` carries the sub-processor into the public notice.

## Personal data (ADR-0023)

- **What:**
  - files people upload, which consumers will fill with profile photos (children's
    included), teaching resources and chat attachments;
  - for each file: its owner, kind, original filename, content type, size and creation
    time.

  This unit itself stores nothing until a consumer ships.
- **Why:** to deliver each consumer's feature. Each consumer states its own purpose.
- **How long:**
  - The row and the object live until the consumer deletes them, or until erasure.
  - After deletion, a non-current version stays in the bucket for up to 30 days and is
    then removed by the lifecycle rule (`dec-cur-retention`).
  - Retention schedules and purges are `cur-content-retention`'s.
- **Who sees it:**
  - Server code receives an `UploadInfo` or a 300-second URL only after the consumer's
    own access check.
  - AWS processes the files as a processor in the EU region.
  - The export hook (`content.uploads`) returns metadata: kind, original name, content
    type, size and creation time, in id order. It returns no URL or key, because a URL
    is not deterministic and a key is internal. Delivering the file bytes in a data
    export is the export unit's job.
  - The erase hook deletes the user's rows, and their objects on commit. It registers
    with `order=900`, so consumers whose rows point at an upload run their erase hooks
    first (they register with a lower order).

## Module boundaries

- **Owner:** `content`.
- It uses `kaleem.platform` (the personal-data registry and `NotFoundError`) and
  `settings.AUTH_USER_MODEL` by string. It imports no business module, so both of
  content's import-linter contracts stay exactly as they are.
- No new event and no new edge.
- `docs/architecture/content.md` is new (ADR-0049 assigned it to this unit). It describes
  the public API, the storage alias, the access rule (decision 3) and the bucket setup.

## Expand/contract and deploy

- Additive only: one new table and one new setting alias.
- The previous release ignores both the table and the variables.
- **Order:**
  1. The owner creates the bucket and IAM user (`hg-cur-storage-credentials`).
  2. The conductor sets the variables on staging (`hg-vps-env`).
  3. The merge, and the deploy that follows it.

  A merge without the variables rolls back by design.
- **Rollback:** the older image ignores the variables and the table. Objects already
  written stay in the bucket.

## Out of scope

- Any endpoint, permission check, type or size validation, quota or EXIF strip.
  Validation and quota are `cur-upload-safety`'s. The endpoints and permission checks
  belong to each consumer.
- Retention purges and the orphan sweep (`cur-content-retention`).
- Offsite copy and the restore drill (`cur-media-backup`).
- Serving files through kaleem's own domain or a CDN.
- A Content-Security-Policy `img-src` entry for the bucket origin. No CSP sets `img-src`
  today. If one is added before `cur-profile-photo`, that unit owes the entry.
- Production's own bucket and env. This spec states the settings, and production's
  values are set when production is stood up (`lb-prod-env-parametrization`).

## Test plan

Backend unit tests (pytest; `content` tests point `STORAGES["uploads"]` at `tmp_path`):

- Settings:
  - `base` has an `uploads` alias of `LocalUploadsStorage` at `MEDIA_ROOT`, and leaves
    `default` and `staticfiles` unchanged.
  - Production with the four variables builds `S3Storage` with exactly the options
    above.
  - Each missing variable raises `ImproperlyConfigured`.
  - A URL signed offline is on `<bucket>.s3.<region>.amazonaws.com`, has
    `X-Amz-Expires=300`, and carries `response-content-disposition` and
    `response-content-type`.
- Services:
  - An upload round-trips its bytes and metadata.
  - The key matches `^u/[0-9a-f]{32}$` and contains neither the filename nor the user
    id.
  - An unknown kind raises `ValueError`.
  - An insert failure deletes the written object.
  - The download URL carries an RFC 5987 Arabic filename.
  - Unknown ids raise `NotFoundError` with code `not_found`.
  - `delete_upload` removes the row at once. Its object goes only when the transaction
    commits, and survives a rollback.
- Personal data:
  - `assert_hooks_honour_contract("content.uploads", ...)` passes.
  - The erase hook deletes the objects after commit.
  - The erase hook's order is 900.
  - `tests/test_personal_data_hooks_cover_every_model.py` stays green with no pending
    entry for `content`.
- Command: `check_upload_storage`'s default, `--keep` and `--existing` modes each pass
  on the filesystem backend. A stubbed failure at each step exits non-zero and names
  the step. The HTTPS fetch is tested with a stubbed opener.
- Catalog: the new message has an Arabic entry (`test_translation_catalogs.py`).

**e2e:** none, with a time budget of 0 s. The unit has no user-facing behaviour. The D3
row reads "`content` — storage: ❌ by design, no user-facing flow; verified by a staging
colour flip".

**Staging colour-flip check** (the unit's definition of done; the conductor runs it
under the staging lock):

1. After the deploy that ships this unit, run
   `docker exec <live django colour> python manage.py check_upload_storage`. It must exit
   0, which proves put, get, the signed URL over HTTPS and delete with the real IAM
   policy.
2. Run it again with `--keep` and note the key.
3. At the next deploy, after the colour has flipped, run
   `check_upload_storage --existing <key>` on the new colour. It must exit 0.
