## The defect the click-through found

`invoice.paid` arrived **80ms before** `checkout.session.completed`:

```
04:18:43.553  invoice.paid               <- carries the period end
04:18:43.561  unknown_subscription       <- no row yet, event DROPPED
04:18:43.633  checkout.session.completed <- creates the row, no period end
04:18:46.281  settle:cs_test_...         <- idempotent, no duplicate
```

A Checkout Session payload has no `current_period_end` and no `items`, so the row is created
with `None` and the UI shows "Active" with no renewal date. Only the nightly reconciler fixes
it — the `reconciled_drift` incidents for users 5 and 7 are exactly this, so it is
reproducible, not a fluke. Logged in `ISSUES.md` rather than fixed on the spot (D10); it needs
its own D1 slice.

This is the argument for click-throughs in one example: 479 backend tests and 363 dashboard
tests are green, `billing` is at 100% line+branch, and none of them caught it — because the
race only exists between two real webhook deliveries.

## Decisions made (link ADRs)

- **[ADR-0027](../../adr/0027-playwright-e2e-harness.md) — the e2e harness exists, is scoped
  to identity, and mirrors the production subdomain topology.** Amends ADR-0021 clause 3 and
  ADR-0026's D3 table. Blocking from day one with a deliberately small suite, because a
  non-blocking gate is one nobody fixes; retries are 1 in CI and a retry-pass is a finding,
  because retries as a flakiness cure turn an intermittent real bug green.

- **[ADR-0026](../../adr/0026-coverage-ratchet-not-aspirational-100.md) — coverage is a
  ratchet floor CI enforces, not an aspirational 100%.** Partially supersedes ADR-0021's
  clause 1. The floor may only go up; **lowering it requires an ADR**. 100% stays the target.
  ADR-0021's e2e clause is explicitly marked **not yet in force** — no Playwright harness
  exists anywhere — and `CLAUDE.md` D3/D9 now say so.
  - The honest framing: this **lowers the stated standard** (100 → 92/97). It trades a number
    nobody enforced for a smaller one everybody does. Recorded as a retreat, not as progress.
  - Root cause worth remembering: the gate stayed off for three months because turning it on
    would have failed every unrelated PR, so the honest answer was always "not this PR". A
    gate whose entire adoption cost lands on whoever touches it next never gets adopted.
    Setting the floor to *what already passes* makes adoption free.

## 2026-09-04 (later) — the security gate runs, and it found something real

ADR-0030 wires `gitleaks` and `pip-audit` into CI as blocking checks and Lighthouse into a
nightly workflow against staging. This was the oldest un-run gate in the project: the
Definition of Done has asked for a security pass and a performance budget since
2026-06-17, and until today the answer was a human saying "reviewed manually" at handoff.
Third time this project has found the same shape — coverage (ADR-0026), e2e (ADR-0027),
now this.

**The first run paid for itself in one command.** `gitleaks` over 439 commits returned 13
findings. Nine are the old MVP's `.envs/` committed wholesale in April: an `sk_live_`
Stripe secret key, an AWS `AKIA` access key *and* its secret, the Django `SECRET_KEY`,
Postgres and Flower passwords. Deleted from the tree, kept by history, on GitHub. Rotation
is now next action #1 — a scanner cannot un-leak anything. Four more were a stray
`portal-snapshot.md` at the repo root: a Playwright accessibility dump from yesterday's
billing click-through, carrying a Stripe test-mode portal session secret. Deleted.

**Allowlisted by fingerprint, not by rule.** `.gitleaksignore` carries one annotated line
per historical finding, so a new secret in a new commit still fails while the known
exposure stays legible. Disabling the `generic-api-key` rule would have been one line and
would have blinded the gate; rewriting history would have broken every SHA quoted in
`docs/` and every submodule pointer, and would still not have revoked a single key.

**Everything was validated locally before the PR** — gitleaks green with the ignore file
and red without it, `pip-audit` clean on the production dependency set in an isolated
venv, `lhci autorun` green against real staging over 3 runs × 2 URLs. Setting a threshold
without measuring first is how you ship a gate that is red on day one and muted by day
three.

**pip-audit is scoped to production dependencies only.** A CVE in `pytest` cannot reach a
user, and a gate that goes red for something harmless teaches people to click past it.
Same reasoning as the e2e table: narrow and honest beats broad and ignored.

Lighthouse floors are ratchets set to measured values (ADR-0026's sense), and the four
audits that keep the categories off 100 — no meta description on marketing, contrast and
console errors and an invalid `robots.txt` on the dashboard — went to `ISSUES.md` rather
than being fixed here (D10).

**Executing the plan found two defects in the plan.** This is the argument for writing plans

- Its model tests created a `Subject` with slug `quran` — which the very next task seeds. They

- **Its `seed_e2e` task was impossible.** It had identity's seed command reset the teacher's

  `curriculum.models` was forbidden. But `identity imports no other business modules` bars

The fix for the second is better than the plan anyway: the e2e specs converge their own
fixture. Each clears the set, sets exactly what it wants, and asserts the *exact* state —
deterministic no matter what a previous run left. Verified by running the suite twice, the
second time against a database the first run had dirtied. Asserting merely "Quran is checked"
would have passed vacuously.

Ruff rejected the test I wrote to cover the abstract base view's stubs (`SLF001` private

`pragma: no cover`.

And Biome rejected `<SubjectsCard role="teacher" />`: a prop literally named `role` on a JSX
element reads as the ARIA attribute. Renamed to `audience`. A lint rule catching a naming

## 2026-09-05 (later) — the keys are rotated, and a documented rule turned out to be wrong

The `588a1e35` credentials are rotated: the `sk_live_` Stripe key, the AWS access key and
secret, the Django `SECRET_KEY`, Postgres and Flower. That was the only *active* exposure on
the whole backlog, open since the first gitleaks run found it on 2026-09-04.

**Then the bookkeeping refused to work.** ADR-0030 clause 2 ends "Removing a line is how a
rotated credential gets recorded as dealt with," and `.gitleaksignore`'s own header says "an
empty file is the goal." Both are wrong, and wrong in a way that would have gone unnoticed
until the next CI run: **rotation makes a credential dead, not absent.** The strings are
still in git history and still on GitHub — `git show 588a1e35:kaleem/.envs/.production/.django`
still prints them. Delete the fingerprints and gitleaks reports them again, on every branch,
forever. The only way to empty the file legitimately is a history rewrite, which the same ADR
rejects two sentences earlier.

So ADR-0030 contained a rule that could not be followed without breaking the gate it created.
ADR-0032 amends it: a rotated credential keeps its fingerprint and gets re-annotated with the
rotation date. The allowlist stops being a to-do list and becomes a rotation record.

Worth noticing *how* this surfaced. The instruction was three words — "all keys rotated" —
and the obvious next move was to do what the docs said. Reading the docs against the actual
state of git history is what caught it. A rule written at the moment of discovery, when the
credentials were live and rotation was hypothetical, did not survive contact with the day
rotation actually happened.

Also corrected `STATE.md`'s `last_green_ci`, which still pointed at meta #146 from the day
before, and the two cross-references that pointed at the now-deleted rotation entry.

## 2026-09-05 (later) — Phase C1: matching, spec to PR in one session

Specced, planned and implemented C1 end to end: **broadcast to every eligible teacher, first to
accept wins, result is a durable `TeacherAssignment`.** Three PRs open — backend#42,
dashboard#35, and the meta pointer bump. Nothing merged yet.

**The decision the design turns on: offers are not rows.** A teacher's inbox is computed live
from open requests minus that teacher's declines. A materialised offer table would go stale the
moment a teacher added a subject or edited availability, and the spec's promise — an unmatched
request is re-evaluated when the pool changes — would then need a job to re-fan-out. Computed,
it is a property of the query. `test_a_request_with_no_eligible_teacher_stays_open_and_becomes_matchable`
exists to make that regression loud: it asserts a teacher who qualifies *afterwards* sees the
offer with nothing re-run in between.

Ran it as 14 plan tasks, each implemented by a fresh subagent and gated by its own review, then
a whole-branch review at the end. **Eight defects surfaced, and most of them were in the plan
rather than the code** — which is the useful finding. Writing the plan out in full, with the
actual code in it, is what made them findable by a reviewer who had never seen the spec.

The two worth remembering:

- **`_student_preference` failed open.** It returned `NO_PREFERENCE` when a student had no
  profile, and `NO_PREFERENCE` is the *most permissive* branch — it admits every teacher,
  including one whose own gender is undeclared. So "we do not know this child's preference"
  meant "any teacher will do": exactly the wildcard C0's gender rule forbids, reached through a
  different door. Unknown must fail closed, and now does, on both the inbox and the accept path.
- **`SubjectsCard` discarded unsaved edits.** Its `useEffect` re-seeded checkbox state from
  *every* server response, so a refetch landing mid-edit silently threw away what the user had
  just clicked — and they then saved what the server already had, believing otherwise. Latent
  for months because the e2e student had no subjects, so stomping an empty response changed
  nothing visible. C1's fixture gave that student a subject and the bug became deterministic,
  turning `subjects.spec.ts` red. Fixing the component rather than making the spec wait was the
  call: waiting would have gone green while hiding a defect a real user can hit.

**Two process notes.**

The coverage ratchet nearly bit. Raising `fail_under` to `97.2` would have turned CI **red** —
coverage.py rounds the measured total to `precision` decimals before comparing, and with the
default precision of 0, `97.28%` compares as `97`. It surfaced only because a review asked for a
root cause of an apparent 0.6pp coverage *drop*, which turned out to be two different `pytest`
invocations measuring different file sets. Neither the drop nor the precision bug was real work
anyone planned; both came out of refusing to accept "the number looks fine".

And the final review earned its keep. It found that the parent — the person who *pays* — could
see nothing: `/assignments/` had been made parent-aware four tasks earlier, and then nothing on
the frontend ever called it. A ruling made correctly at Task 8 simply failed to carry into
Task 12, and each task's own scoped review was too narrow to see the gap. That is precisely the
class of defect a whole-branch pass exists for.

## 2026-09-05 (later still) — Phase C2: booking + quota

Specced, planned and implemented C2 in the same session as C1: a student claims a standing weekly
slot, a daily idempotent job materialises the cycle's sessions up to quota, and either side can
cancel — 24 hours ahead returns the unit, and a teacher's cancellation always does. Three PRs open.

**`sessions_per_cycle` has been on the plan model since July and nothing had ever read it.** A
parent could buy four sessions a month and receive none. That is the hole this closes.

**The find that mattered was not in C2 at all.** Building it, an implementer hit `ProtectedError`
deleting a student, stopped, and asked rather than working around it. I reproduced it: **account
deletion has been broken in production for every student who was ever matched.**
`TeacherAssignment.source_request` was `PROTECT`, and Django's collector evaluates `PROTECT` per
cascade branch without deferring long enough to notice the protecting row is itself being deleted
by a sibling branch. The GDPR erasure task sitting under *Blocks launch* would have walked straight
into it. Both that field and C2's new `Session.slot` are now `RESTRICT`, which still refuses an
orphaning delete but permits a same-operation cascade.

Worth recording that I got the reasoning wrong twice on the way there. I kept `Session.assignment`
as CASCADE because "TeacherAssignment cascades fine from User" — it did not, that *was* the bug —
and kept `Session.slot` as PROTECT because "nothing hard-deletes a RecurringSlot" — untrue, since
deleting a user does, transitively. Both conclusions survived; both premises were false. The ledger
records the falsified reasoning next to the correction, because the next person to read those two
`on_delete`s will otherwise rebuild the same wrong model of them.

**What green tests did not catch.** Three defects this phase would have shipped behind a passing
suite:

- A test that **fails one day in seven**. The refill test cancelled "a far-future session" that was
  actually the next Saturday — inside the 24-hour window whenever CI runs between Friday and
  Saturday morning. It passed on the day it was written.
- A fixture change of mine that **broke a suite in the other repository**. Making the seed
  self-accept a match request removed the unaccepted state `matching.spec.ts` asserts. The backend
  implementer could not have seen it; I found it by running the suite rather than reading the
  report. One student cannot be both unmatched and booked — so there are two students now.
- A **teacher seeing a red error box** on `/schedule`, because `QuotaBadge` rendered
  unconditionally against a student-only endpoint. Every component test passed; each mocked the
  hook it was handed. Only a real browser with a real teacher session showed it.

**And a file that documented a rule it did not enforce.** The final review found `DELETE /slots/`
was never given the student gate my own ruling ordered — while the comment written to record that
ruling asserted it had been. The deferred "no API-layer 403 test on that view" was exactly why it
slipped. A teacher could have ended a student's standing lesson time.

**One root cause, three symptoms.** Multi-subject booking refused, parents unable to claim, the
slot-read endpoint narrowed to students — all because `claim_slot` takes no parameter naming the
student or the subject. `ISSUES.md` logs that as one item rather than three, because three entries
would have three people fixing the same thing badly.

## C3a — video rooms, and no video

Phase C3 was going to be a Zoom adapter. It is not: the user chose to build kaleem's own 1-on-1
WebRTC service, which reverses ADR-0011 and cost **group sessions their place in v1**. ADR-0034
records both, along with the two things the reversal makes mandatory and neither of which exists
today — a TURN server (roughly one connection in six cannot go peer-to-peer and fails outright
without a relay) and ASGI/Channels for signaling, which production does not serve.

Two facts made the reversal cheaper than ADR-0011 priced it. Zoom's free tier caps *every*
meeting at 40 minutes against kaleem's 60-minute lessons, so the "free" v1 path never existed.
And the 6–12 month estimate priced an SFU with group and recording; restricted to 1-on-1, media
goes peer-to-peer and the backend reduces to signaling plus authorization. That is a different
engineering category. So video became five slices, and **C3a deliberately contains none of it** —
the room lifecycle, the authorization guarding it, and the provider seam are identical whether
media ends up P2P, an SFU, or a vendor, so they ship first behind a fake.

**The spec I wrote was wrong twice, and the plan caught it.** Writing the plan meant reading the
code the plan must name, which surfaced both: I had specified a 503 where `platform/drf.py` maps
`ExternalServiceError` to **502** (and documents why — 503 claims kaleem itself is down), and I
had promised "a distinct typed code per failure" when the API error body is `{"detail": ...}` with
no code field at all. The second correction changed the design rather than a constant: the
countdown is now driven by `can_join_at`, so a well-behaved client never provokes the window
error, and the 409 is a backstop for a stale tab rather than control flow.

**What green tests did not catch — five, this time, all the same species.** Every one was a test
that looked like coverage without being coverage:

- **The row lock was untested.** The "one room per session" test made three *sequential* calls and
  passed with `select_for_update` deleted — while the spec named concurrency as the primary guard
  and the unique index as merely the backstop. It now takes real threads, a barrier, and a
  deliberately slow provider; removing the lock produces a genuine `IntegrityError`.
- **The lock was also far wider than recorded.** `select_related("assignment__subject")` means
  Postgres locks the `Subject` row too, and there are about three subjects platform-wide — so one
  student joining a Quran lesson would have serialized every Quran join once a real provider does
  I/O. I had already accepted a deferral on this, with a bound wrong by orders of magnitude.
  Both mitigations were one line each, so the right move was to stop deferring it.
- **A teacher who is also a parent would have seen no Join button** on lessons they teach. The
  parent guard reused `resolveViewerRole`, a display heuristic where "parent wins" is correct for
  choosing which names to show and wrong as a capability gate. Now server-computed per row.
- **The seed's idempotence test could not detect the bug it existed to forbid.** The command resets
  the student's rows every run, so "run it twice, count is stable" passes whether the code
  repositions a session or creates an extra one. Pinning the count *within* one run against the
  plan's quota is what distinguishes them.
- **The countdown said "Opens in 19791 min."** Unit tests only exercised times near the boundary;
  the e2e asserts only disabled-versus-enabled, never the label. Sessions generate weekly for a
  whole cycle, so *most* rows looked like that. Found in a browser, in the D9 walk, which is
  precisely what that step is for.

**A false claim of my own.** I recorded that I had verified the dashboard suite against raised
coverage floors. I had verified the working tree; only one of four floors was ever committed. The
verification was real and ran against a file that was not in the branch. The final review caught
it. Worth remembering that "I checked" and "the branch contains it" are different statements.

**One duplication I refused to carry.** Two functions restated "the actor is this assignment's
teacher or student". Normally a deferred minor — but one gates entry to a video call with a child
and the other decides whether the UI offers it, so a future widening that updates one and not the
other fails silently onto safeguarding. Widening is now one line in one place.

Backend 753 at 98.16% (floor 97.3 → 98.1); dashboard 543 at 93.63/90.48/86.69/93.63 (floors →
93.5/90/86.5/93.5); e2e 30 → 33. Verified by hand as a student in English, a student in Arabic
with RTL, and a teacher.

**What ships is honest about itself:** clicking Join mints a real, per-user, authorized grant and
opens a tab at a host that does not resolve. That is C3a finished, not C3a broken.

## C3b — signaling, and the bug a green suite could not see

Phase C3b split signaling into its own service — escape hatch **E5**, which the roadmap marks
*"not pre-approved… requires a full ADR with evidence."* Half its trigger genuinely fits (long-lived
connections are the shape a WSGI monolith handles worst); the other half does not (no production,
no users, no measured pain). **ADR-0035 says the evidence is architectural rather than observed**
rather than dressing it up, because a reader in six months should find the weakness written down
instead of reconstructing it.

The split earned one thing immediately: a separate process cannot ask the database whether a grant
is genuine, so C3a's forgeable token had to become HMAC-signed and verified. That closed a
*Blocks launch* entry as a **precondition** rather than a someday.

**The finding that matters.** The final whole-branch review ran the service under real uvicorn —
something no test does — and found the capability token written to the log on every single
connection:

```
INFO: "WebSocket /ws/rooms/session-42?t=eyJleHBpcmVzX2F0IjogMTc4ODY0OTc1M…OEE" [accepted]
```

A live grant to one child's video room, sitting in `docker logs` for its full thirty-minute life,
replayable by anyone who can read them. `--no-access-log` would not have stopped it (different
logger). Ninety-two signaling tests were green throughout, because **every one of them runs
in-process through Starlette's `TestClient`** — uvicorn, Traefik and TLS are all below the layer the
suite touches, and the bug lived exactly there. I reproduced it myself before accepting it, and
again after the fix.

Chasing it turned up a second: Traefik's access log carried the token too, its `redact` option is
**silently ignored** for core field names, and it has no per-router configuration. So the choice was
a gateway that logs capability tokens or a gateway that logs no paths at all. We took the second and
compensated with gunicorn's own access log for the API — a real, platform-wide observability loss,
recorded rather than glossed. The actual fix is to move the token out of the URL entirely; that is
C3c's, and it is filed.

**Eight findings, one species.** Across C3a and C3b nearly every review finding has been the same
thing: a test or a comment that reads as a guarantee and is not one. A docstring contradicting its
own error messages. An unreachable branch. A test whose *name* said "unknown room" while its body
used a full one. A malformed-token test whose five cases were all ASCII — so the `TypeError` crash
its name promised to prevent was the one case it never tried. A contract whose comment claimed it
forbade Django while its list held only eleven `kaleem.*` modules, so `import django` passed CI
green. Bad-message tests that accepted *any* close code, when three distinct codes are the entire
point. A "no email in the URL" assertion that could not fail because no email ever went near the
URL. The suite is not what caught these. Review was, every time.

**A ratchet held.** Bringing `signaling/` into coverage for the first time dropped the total to
97.59 against a 97.6 floor, and the honest options were to test three error paths or write an ADR
lowering the ratchet. Lowering would have recorded our own omission as the new normal, so we tested
them — including the one that proves a peer whose socket dies does not take the surviving call
with it. Coverage finished at 97.78 and the floor went **up**.

**Two of my own corrections.** I reported `httpx` as "already installed but undeclared"; it was
residue from a subagent's throwaway `pip install` in a container a rebuild later replaced — the
ruling to settle it by rebuild rather than argument was right, the reason I gave was reading state
that was not real. And I demanded a test for a property that **cannot be tested** (a join to a
non-existent room can never be refused), which cost a round and produced a name/body mismatch from
an implementer trying to satisfy an impossible instruction.

Backend 852 at 97.78%; `lint-imports` 11 kept / 0 broken, the new contract broken deliberately in
**both** directions; e2e unchanged at 33 and said so in the D3 table rather than quietly claimed.
Walked by hand over real sockets: presence, relay, departure, and every refusal code.

**What ships is a relay with no client.** No browser code, no TURN — so no call connects, and
roughly one in six will need a relay even once C3d exists. That is C3b finished, not C3b broken.

**Shipped and verified on staging the same day.** `deploy-staging` succeeded on the first attempt
because the VPS `.env.production` was edited before the merge landed, which is the one thing that
could have turned it red — `ship.sh` would have rolled the whole colour back on a 503 from the
signaling health check. `https://ws-staging.kaleem.academy/health/live/` answers
`{"status":"healthy"}` over a valid certificate, so the deployed secret is present and usable.
It still does not prove the API holds the *same* secret; nothing in the deploy can, and the first
real proof will be a successful join once C3d exists.

Energy: 3.

**Session close 2026-09-06.** C2, C3a and C3b all shipped and verified on staging within two
days: booking + quota, the video room and its provider seam, and an authenticated signaling
service split out under E5. `deploy-staging` green on the first attempt each time. Phase C is

## C3c — STUN/TURN, and three hardening items (2026-09-06)

**What shipped.** A self-hosted `coturn` relay on the staging VPS with HMAC-derived ephemeral
credentials, delivered to the browser as `ice_servers` on the existing join grant. Plus three
things that ride the same grant and the same deployable: the capability token moved out of the
URL query string into `Sec-WebSocket-Protocol`, a room is now pinned to one deploy colour, and
`GRANT_TTL` is deleted.

Backend 881 at 97.76%; dashboard 544 with floors ratcheted to 93.6/90.4/86.6/93.6; e2e unchanged
at 33 and recorded as `❌ by design` in the D3 table rather than quietly claimed. `ruff`, `mypy`,
`lint-imports` and `makemigrations --check` all clean.

**The plan contained a Critical, and an implementer caught it.** The `turnserver.conf` I wrote
had `static-auth-secret=${TURN_SECRET}`. **coturn performs no variable expansion in its config
file**, so that sets the shared secret to the literal string `${TURN_SECRET}` — not a broken
deploy but an *open relay*, with a publicly guessable secret letting anyone mint credentials and
use kaleem's relay as a proxy and a DDoS amplifier. It would have passed every gate: there is no
test suite in `infra`, `docker compose config` resolves happily, and coturn starts. The fix is to
pass it as a CLI argument, which Compose *does* expand. The lesson is not "review configs" — it
is that **a config language's non-features are invisible to every gate we own**, and the only
thing that would have caught this is the live `turnutils_uclient` check the spec already
mandated. The subagent raised it as a mild "worth a smoke test"; the severity was mine to assign.

**`ISSUES.md` promised a fix that does not exist, and C3c withdraws it.** C3b dropped Traefik's
`RequestPath` from the access log because it carried the signaling token, and recorded that the
field could be restored once the token moved. It cannot. `config/urls.py` includes `allauth.urls`,
which serves `/accounts/confirm-email/<key>/` and `/accounts/password/reset/key/<uidb36>-<key>/` —
single-use **account-takeover** credentials in the **path**, not the query string. Moving one
credential out of one query string changed nothing about whether logging paths is safe. Dashboard
and marketing get their path-level visibility from their own container access logs instead. Worth
noting how the wrong belief survived: it was written down as a plan, and a plan in `ISSUES.md`
reads as a decision rather than a hypothesis.

**The split-room fix in `ISSUES.md` was also incomplete.** It proposed per-colour WS hostnames so
a room could not straddle a deploy. But `django-blue` and `django-green` both claim
`Host(${API_DOMAIN})` too, so two participants could be served their grants by *different Django
colours* and straddle anyway. Hostname pinning narrows the window; it does not close it. The
actual fix is `Room.signaling_url` — the colour becomes a property of the room, written by the
first joiner under the session row lock that C3a already added, replayed to everyone after. The
trade is deliberate: a room pinned to a stopped colour now fails a rejoin **loudly**, where before
it silently succeeded into a split room.

**The coverage ratchet did not move, and that is the honest outcome.** Measured 97.76%. Tried
`fail_under = 97.8` and it failed — "Required test coverage of 97.8% not reached. Total coverage:
97.76%" — even though the report *displays* `97.8%`. So `pyproject.toml`'s comment about
`precision = 1` rounding the total before comparison describes a rule coverage.py does not appear
to follow. Reverted to 97.7 and logged the contradiction rather than leaving a knife-edge floor;
this project has been bitten twice by exactly that.

**Also found:** there is no `docs/architecture/scheduling.md`, and there never has been. C0, C1,
C2, C3a and C3b each silently skipped that line of D9. `scheduling` is now the largest module in
the codebase. Logged rather than faked — a TURN-only architecture doc would misrepresent the
module more than its absence does.

**What ships is still not a call.** C3c has no browser code. `RTCPeerConnection`, the video grid
and the controls are C3d, which is the first phase that can produce a working call. What exists
now is a relay, credentials for it, and a signaling handshake that no longer leaks its own
credential.
