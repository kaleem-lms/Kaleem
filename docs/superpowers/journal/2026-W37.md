## Shipped this week

**CI cost optimization** (ADR-0038, spec
`docs/superpowers/specs/2026-09-08-ci-cost-optimization-design.md`, backend/dashboard/marketing
untouched — this is a meta-repo-only change to `ci.yml`, `dependabot.yml`, `lighthouse.yml` and
`stripe-clock.yml`). Twenty-six of the last sixty meta PRs (43%) touched only `docs/**` and ran
the full eight-job suite anyway; every merge then re-ran the same suite a second time on a tree
its PR had already proved. A single `triage` job now emits `code` (is this change even capable
of breaking anything code-shaped) and `verified` (has a green PR run already proved this exact
git tree, via a content-addressed artifact). All seven gate jobs share one condition on both.
`timeout-minutes` went on every job — `ci.yml` had none, and GitHub's 360-minute default meant
one hung process could cost more than two weeks of this change's savings. Dependabot trimmed to
the one ecosystem that produces anything and moved to weekly; Lighthouse and the Stripe
test-clock harness moved nightly → weekly.

**Verified on the real merge, with the prediction recorded before it happened.** PR #190 merged
to master (`480b78b`). The tree hash of the merge ref was known and its artifact was on record
before the push ran, so this was a falsifiable check, not a post-hoc reading: run `34206968953`
showed `triage` reporting `code=true verified=true`, all seven gates `SKIPPED`,
`deploy-staging` green through all 14 steps, and staging live afterward (checked on all four
public surfaces). Cost: 4 billed minutes against an 18-minute baseline for a push — a 78% cut
on that one merge, holding the modelled shape.

## The plan had a step that could only ever return one answer

Task 2 planned to prove `code=false` in CI by pushing a docs-only probe commit to the feature
branch and reading the result. It couldn't work, and not for a subtle reason: `ci.yml` triggers
on `push` only for `master`/`main`, so a push to a feature branch fires nothing at all — every
run on this branch was necessarily a `pull_request` run. And on a `pull_request` event GitHub
resolves the workflow from the **merge ref**, so the diff always includes this branch's own
`.github/**` changes. There is no arrangement of branches that produces a docs-only diff while
also running the new `triage` job for the first time — proving `code=false` in CI was
structurally impossible until a genuinely docs-only PR existed, which could only be this one,
closing the spec. The step was withdrawn rather than retried, and the false path first ran for
real on this very PR.

Worth naming precisely: this is a different shape from the project's recurring "the verifier is
itself unverified" failure. Nothing here silently passed while proving nothing — the plan asked
a real question that its own environment could not answer, and the mistake was caught before
any run, by reading the trigger conditions rather than by a red run.

## Two Important defects, one of them self-inflicted by the same task's hardening

The whole-branch review of the job-gating task found two:

1. **No Dependabot actor clause on `deploy-staging`.** The seven gates already skip for
   `github.actor == 'dependabot[bot]'`, but if a Dependabot PR were ever merged by Dependabot
   itself (`@dependabot merge` / auto-merge), the resulting push would carry the same actor —
   every gate would skip, nothing would read `'failure'`, and the deploy would ship a change no
   gate had ever seen.
2. **Missing `!contains(needs.*.result, 'cancelled')`, and this one is worth sitting with.**
   `!cancelled()` is a run-level signal, false only when the *entire* workflow run is cancelled
   — it does not cover one job being individually killed. This exact diff is what introduced
   `timeout-minutes` on every job for the first time, which made an individually-timed-out job
   newly reachable. Without the extra clause, a `backend-test` hung past its 10-minute cap would
   report `cancelled` in `needs.*.result`, and `deploy-staging` would ship a tree whose test
   suite never actually finished. The cost ceiling this task added created the exact gap its own
   deploy-guard needed to close. Both findings were fixed in one review round and re-verified on
   a real CI run (7/7 gates success, `deploy-staging` correctly skipped on that PR run).

## The cost baseline was one unlucky sample of a job that swings 3.5x

The spec's original 14-minute PR / 18-minute push figures came from a single run. Measuring 11
pre-change runs while writing the closing docs: PR median 15 (range 13–16, n=6), push median 18
(range 17–19, n=5, unchanged). The push figure held; the PR figure was one minute optimistic.
Cause: `dashboard-lint`'s coverage step ran 83–296 seconds **for identical work** — same
`dashboard` submodule pointer, same 112 test files, same coverage numbers in the fastest and
slowest of the 11 runs. A 3.5x swing on the single largest job in the suite, and the original
sample happened to land at its slow end. Corrected model: baseline ~10,040 min/month (~$64),
after ~4,650 (~$21). The 54% headline is unchanged — it comes from not running jobs at all,
which timing variance inside a job that still runs does not touch.

## What actually verified, and what is honestly still open

The guard's *positive* lookup — an artifact existing and being found — was proven twice: once
mechanically (a direct `gh api` query against a just-uploaded artifact returned 1) and once for
real, on the master merge above. Its *negative* path — a push whose tree has genuinely no
recorded artifact, so the full suite has to run — has never happened on a real push. The
runbook (`docs/runbook/ci.md`) says so plainly and gives the two ways it will occur on its own
(7-day artifact expiry; `master` moving under a PR) and how to force it deliberately. Same
honesty for Dependabot: three real Dependabot PRs are open (#182, #183, #184) and the actor
clause has only ever been read, never exercised against an actual Dependabot event.

**The consequence worth remembering past this week:** Dependabot PRs now report green with
nothing tested, where they used to report red with nothing tested. Red was honest; green is
not, and if branch protection is ever turned on for this repo — it isn't today, GitHub Free has
none — a skipped required check counts as satisfied. `ci.yml` pins `upload-artifact@v4`, and
#183 is exactly that dependency's real upgrade, sitting behind a tick that verified nothing.
Logged to `ISSUES.md` rather than merged on the strength of the tick.

## 2026-09-08 — addendum: the premise was false, and I had the evidence in hand

The final whole-branch review checked the one thing I never did: **`kaleem-lms/Kaleem` is a
public repository**, and has been since it was created in 2024 (`PublicEvent` carries the same
timestamp as `created_at`). Standard GitHub-hosted runners are free on public repos. Verified
three ways: `gh api /repos/kaleem-lms/Kaleem` reports `private: false`; an unauthenticated
`curl` of the API returns 200; and `actions/runs/<id>/timing` reports
`billable.UBUNTU.total_ms: 0` for the pre-change baseline run *and* the post-change merge run,
with `run_duration_ms` populated — so the endpoint works and the answer is zero. All five
submodules are private but carry **zero workflows**, so nothing is billed anywhere either.

Everything this change was justified by — "~$62/month", "~9,700 billed minutes", "get under the
2,000-minute allowance" — is arithmetic on a bill that does not exist.

**The part worth keeping is that I saw the disconfirming evidence in the first five minutes and
explained it away.** The opening survey ran `/actions/runs/<id>/timing` across five runs, got
`total_ms: 0` every time, and I wrote it off as a broken endpoint because `gh repo view` had
just said `PRIVATE` and a `rulesets` call had 403'd with "Upgrade to GitHub Pro or make this
repository public". Two readings disagreed; I kept the one that made the task make sense and
discarded the one that did not, without spending the single command it would have taken to
settle it. I cannot now reconstruct why the first `visibility` read said `PRIVATE` — the current
answer is unambiguous and repeatable — but that uncertainty is the point: the contradiction was
visible and unresolved, and I proceeded anyway.

This is the same failure this project keeps naming, one level up again. C3b: the suite could not
represent the thing it claimed to test. C3d: the e2e passed locally under a deleted override and
could never have passed in CI. Here: the measurement was sound and the *premise under the
measurement* was never checked. Measuring carefully is not the same as measuring the right thing.

Two consequences beyond the wasted justification:

1. **A live credential exposure, pre-existing and now confirmed.** `KaleemC3d!2026` and
   `KaleemStaging!2026` were served to an anonymous `curl` from `STATE.md` on `master`. They are
   removed from the tree and stay in history. Logged under *Blocks launch* with the rotation list.
2. **ADR-0038 made `security` (gitleaks) skip on documentation-only changes** — and root-level
   `*.md` is documentation. This project's one previous leak was `portal-snapshot.md`, a
   root-level `.md`, found by the first `security` run. On a public repo that delay means
   world-readable until the next code PR. The fix now costs nothing, because minutes are free.

The docs branch `docs/ci-cost-optimization-close` is committed and deliberately **not merged**.
Merging it would publish a permanent record built on the false premise. The mechanism is sound
and stays; the justification has to be rewritten around wall-clock and noise, which are real.

## 2026-09-11 — the correction needed correcting, and the invoice was one call away

Picked the held docs branch back up. Before rewriting ADR-0038's justification around
"the repo is public so runners are free", I checked that premise — and it does not reproduce.
`gh api /repos/kaleem-lms/Kaleem` reports `private: true`, `gh repo view` agrees, and an
unauthenticated `curl` of both the API and `raw.githubusercontent.com/.../master/STATE.md`
returns 404. The repo owner confirms: it was public on 09-08 and they made it private since.

So the 09-08 addendum's *finding* (the passwords were briefly world-readable) was real, and
its *explanation* (therefore runners are free, therefore no bill) was not. Two things were
wrong with it:

1. **`billable.total_ms: 0` proves nothing.** It was the load-bearing evidence for "public",
   and it returns 0 on this repository *while private*, including on a full eight-job,
   501-second run. An unreliable field read as a fact, twice, in opposite directions.
2. **The real invoice was readable the whole time.** The spec recorded that
   `/orgs/{org}/settings/billing/actions` returns `410 This endpoint has been moved` and
   treated that as the end of the road. The endpoint it moved *to* —
   `/organizations/{org}/settings/billing/usage` — answers with the plain `repo` scope this
   session already had. It reports 115 / 114 / 351 / 72 / 2,098 Actions minutes for
   April / May / June / August / September 2026, gross $0.69–$12.59, **discount equal to
   gross, net $0.00 in every month on record.**

The modelled baseline of ~10,040 min/month was about **5× the actual** usage in the month the
change landed. The overage rate is $0.006/min, not $0.008.

What that does to the decision: nothing. The mechanism is verified and stays. Its
justification is now wall-clock and signal — a docs PR waiting ~15 minutes for eight jobs that
cannot learn anything about it — plus one small real cost argument that only became true
afterwards: the repo is private now, so its minutes are metered against a 2,000/month
allowance that September's 2,098 has already crossed.

**The shape of the mistake, said plainly.** Last week I wrote that the lesson was "measuring
carefully is not the same as measuring the right thing", and then corrected the premise
without measuring *that* either — I swapped one unverified explanation for another that
happened to be available, and stopped. A `410` was read as "unavailable" rather than as
"moved", which is what it literally says. The branch was held for the right reason and the
held version would still have published something false.

Also downgraded, correctly: the credential entry in `ISSUES.md` no longer claims an open
exposure, because the window is closed. It still says rotate — history keeps what was public,
and anyone who cloned during the window kept it too.

Rewritten: ADR-0038 (Context, Alternatives, Consequences, plus a Correction section carrying
the full account), a correction banner on the spec with its body left unedited as the record
of what was designed, `STATE.md`, and `ISSUES.md` — where the gitleaks-skips-docs problem is

## 2026-09-11 — C4a: the call learns to work without permission

Phase C re-opened as C4 after the user said the call's UI was bad and named four things:
no in-call device selection, no way to join without granting camera and microphone, no way
to join with the camera already off, and no screen share.

Two of the four were not UI problems. `usePeerConnection` created its senders at
first-track-attach, so no media meant no `m=` lines and a call that could never negotiate —
the UI hid that by refusing to show Join until `getUserMedia` resolved. A screen track was a
second video track with nowhere to go. ADR-0039 answered both by negotiating three lines
before the first offer, so every later change is `replaceTrack` on an existing line. The
single-offerer rule and the absence of `onnegotiationneeded` both survive untouched.

Eight tasks, executed subagent-driven: fresh implementer per task, a review after each, a
whole-branch review at the end. Shipped as dashboard#43 and backend#50.

### The plan was wrong in a way only a browser could show

ADR-0039 said both peers create the three transceivers identically. That is impossible, and
Task 8 — the first honest browser run — measured why in a blank page with no React and no
signaling: **a remote offer's `m=` section may only be matched to a transceiver created by
`addTrack()`**; `addTransceiver()` ones are reserved for that side's own next offer. An
answerer creating three went 3 → 6 transceivers and associated none. So `ontrack`'s identity
check never matched and the answer was `recvonly` on every line.

**Both peers reported `connected` while zero media flowed in either direction.**

804 unit tests were green over it. The reason is the one this project keeps re-learning: the
test double handed `ontrack` back the same transceiver objects the code had created, so "the
browser refuses to associate yours" was *unrepresentable* in it. Not a missing test — a
harness that could not express the failure. The fix: the offerer creates, the answerer adopts
and flips to `sendrecv` before `createAnswer`, and tracks route by wire position. The ADR
amendment records the measurement, and says plainly that the design held and the
implementation clause did not.

Worth keeping: the implementer ruled out timing and object identity *first*, by measurement,
before concluding the browser was at fault. "Chromium is wrong" was the least likely of three
candidates and had to be earned. It was earned.

### Seven inert assertions, none found by the suite

Every task review found at least one assertion that could not fail. Two were in test code I
wrote into the plan myself: a `sendrecv` check that tested the fake's default rather than what
production passed, and a "never re-offers" check asserting against code paths the effect
cannot reach. Others: absence assertions satisfied by a swallowed `TypeError`; `supported`
never asserted true, so a constant `false` would hide the share button in every browser while
seven tests stayed green.

Every one was caught by review, none by running the suite. That is the whole argument for the
review step, and it is not an argument about carelessness — these were written by people
trying, against a plan that had already named the risk.

### Lint was red for three tasks and no review saw it

I told implementers to run vitest and tsc, and told reviewers not to run anything. `pnpm lint`
had been failing since Task 4 and would have gone red at PR time. Fixed by making lint part of
every implementer's finish criteria. A gate nobody was asked to check is a gate that is not
running, and the instruction was mine.

### Removing a thing exposes what depended on it invisibly — twice

Removing the Lobby join gate (a ruling I made mid-plan, reversing my own scoping) removed an
accidental synchronisation point: `enableLobbyCamera` only ever clicked, and its six callers
were synchronised by "Join now" not rendering until a stream existed. `session-ui.spec.ts`
measures the page immediately afterwards and started failing in CI. The helper's docstring
still asserted the old contract in prose, so a stale guarantee outlived its mechanism — the
second time on this branch a comment kept promising something the code had stopped doing.

Also: that same ruling created one of the two final-review blockers (a screen share started
before the first offer going nowhere, silently).

## 2026-09-11 (later) — C4b: what a browser knew that 297 tests did not

C4a gave the call its capability; C4b put it in front of the user. Seven TDD tasks,
subagent-driven, fresh reviewer per task plus a whole-branch review. Shipped as dashboard#46.

### Three defects, all invisible to a green suite

**A phantom screen tile on every call.** ADR-0039 negotiates a screen media line whether or
not anyone shares, and a pre-negotiated line always delivers a receiver track — so
`remoteScreen` was non-null on every call and C4b consumed it as "someone is sharing".
Measured on an ordinary lesson: a blank 1280×720 tile took the main slot, the other person
was demoted to a 144×81 thumbnail, the auto-switch burned at connect, and the stored layout
was clobbered. Fixed by gating on **frames** — the mechanism Task 1 had already established —
rather than on the stream existing. Two separate branch failures recovered from that single
fix, unedited, which is the strongest evidence available that the root cause was right.

**The self view was 0% visible in the default layout.** A 224×126 card at y=-62 inside an
81px wrapper. It passed at full coverage because *every layout assertion in the suite was a
className regex*. A class string cannot tell you whether an element is on screen. That is the
structural lesson of this branch, and the fix was not a better regex — it was a real
`boundingBox()` assertion, which turns red the moment the bug is reintroduced.

**A stopped share trapped the viewer.** The frozen screenshot kept the main tile for the rest
of the lesson, the teacher stayed a thumbnail, and `mainIsScreen` overrode the viewer's own
spotlight choice in all four layouts. Only a reload escaped. I had filed the underlying
detection gap as follow-up after seeing it measured; the final review traced what a *user*
experiences and showed the trap was not tolerable even if the detection is. Measuring a thing
and understanding its consequence are two different acts.

### The inert-assertion count reached ten

Every task review found at least one assertion that could not fail. Notable ones: a
focus-restoration test that passed because focus never left the control in the first place
(caught by the *implementer*, the first time that has happened here); a storage-validation
test rendered vacuous by a `vi.spyOn` leaking from the preceding test, so deleting the
validator left all six green — it only failed when run in isolation; and the Undo toast,
Task 6's entire stated point, with zero coverage, where deleting the toast block left 888
unit and 50 e2e tests green while users silently lost the feature.

Ten found, nine by reviewers. The suite has never once caught one. That is not a claim about
carelessness — every one was written by someone trying, against a plan that had already named
the risk in writing.

### Measure before fixing, twice vindicated

The final review computed that the control bar's six targets would shrink below 44px at
360px. Asked to measure rather than act on the arithmetic, the implementer found all *seven*
targets (the review had miscounted) were exactly 44×44 and did not shrink — the real defect
was the row overflowing, with Mute clipped at x=-6 and a 14px horizontal page scroll. A fix
based on the hypothesis would have shrunk targets that were already correct and left the real
bug in place.

Same shape in C4a: "Chromium refuses to associate our transceivers" was the least likely of
three candidates and had to be earned by ruling out timing and object identity first.

### I put two false claims into dispatch briefs

That e2e specs depended on a `share-screen` testid (nothing referenced it), and that
`Lobby.layout.test.tsx` measured `scrollWidth` (it never did, at any commit). Both caught by
reviewers. Implementers treat a brief as authoritative, so a wrong one sends them defending a
constraint that does not exist. Check before asserting — the same discipline this branch kept
demanding of everyone else.
