## Shipped this week

**CI cost optimization** (ADR-0038, spec
`docs/superpowers/specs/2026-09-08-ci-cost-optimization-design.md`, backend/dashboard/marketing
untouched — this is a meta-repo-only change to `ci.yml`, `dependabot.yml`, `lighthouse.yml` and

the full eight-job suite anyway; every merge then re-ran the same suite a second time on a tree

one hung process could cost more than two weeks of this change's savings. Dependabot trimmed to

to master (`480b78b`). The tree hash of the merge ref was known and its artifact was on record
before the push ran, so this was a falsifiable check, not a post-hoc reading: run `34206968953`
showed `triage` reporting `code=true verified=true`, all seven gates `SKIPPED`,
`deploy-staging` green through all 14 steps, and staging live afterward (checked on all four
public surfaces). Cost: 4 billed minutes against an 18-minute baseline for a push — a 78% cut
on that one merge, holding the modelled shape.

## The plan had a step that could only ever return one answer

Task 2 planned to prove `code=false` in CI by pushing a docs-only probe commit to the feature
branch and reading the result. It couldn't work, and not for a subtle reason: `ci.yml` triggers
on `push` only for `master`/`main`, so a push to a feature branch fires nothing at all — every
run on this branch was necessarily a `pull_request` run. And on a `pull_request` event GitHub
resolves the workflow from the **merge ref**, so the diff always includes this branch's own
`.github/**` changes. There is no arrangement of branches that produces a docs-only diff while
also running the new `triage` job for the first time — proving `code=false` in CI was
structurally impossible until a genuinely docs-only PR existed, which could only be this one,
closing the spec. The step was withdrawn rather than retried, and the false path first ran for
real on this very PR.

Worth naming precisely: this is a different shape from the project's recurring "the verifier is
itself unverified" failure. Nothing here silently passed while proving nothing — the plan asked
a real question that its own environment could not answer, and the mistake was caught before
any run, by reading the trigger conditions rather than by a red run.

## Two Important defects, one of them self-inflicted by the same task's hardening

The whole-branch review of the job-gating task found two:

1. **No Dependabot actor clause on `deploy-staging`.** The seven gates already skip for
   `github.actor == 'dependabot[bot]'`, but if a Dependabot PR were ever merged by Dependabot
   itself (`@dependabot merge` / auto-merge), the resulting push would carry the same actor —
   every gate would skip, nothing would read `'failure'`, and the deploy would ship a change no
   gate had ever seen.
2. **Missing `!contains(needs.*.result, 'cancelled')`, and this one is worth sitting with.**
   `!cancelled()` is a run-level signal, false only when the *entire* workflow run is cancelled
   — it does not cover one job being individually killed. This exact diff is what introduced
   `timeout-minutes` on every job for the first time, which made an individually-timed-out job
   newly reachable. Without the extra clause, a `backend-test` hung past its 10-minute cap would
   report `cancelled` in `needs.*.result`, and `deploy-staging` would ship a tree whose test
   suite never actually finished. The cost ceiling this task added created the exact gap its own
   deploy-guard needed to close. Both findings were fixed in one review round and re-verified on
   a real CI run (7/7 gates success, `deploy-staging` correctly skipped on that PR run).

## The cost baseline was one unlucky sample of a job that swings 3.5x

The spec's original 14-minute PR / 18-minute push figures came from a single run. Measuring 11
pre-change runs while writing the closing docs: PR median 15 (range 13–16, n=6), push median 18
(range 17–19, n=5, unchanged). The push figure held; the PR figure was one minute optimistic.
Cause: `dashboard-lint`'s coverage step ran 83–296 seconds **for identical work** — same
`dashboard` submodule pointer, same 112 test files, same coverage numbers in the fastest and
slowest of the 11 runs. A 3.5x swing on the single largest job in the suite, and the original
sample happened to land at its slow end. Corrected model: baseline ~10,040 min/month (~$64),
after ~4,650 (~$21). The 54% headline is unchanged — it comes from not running jobs at all,
which timing variance inside a job that still runs does not touch.

## What actually verified, and what is honestly still open

The guard's *positive* lookup — an artifact existing and being found — was proven twice: once
mechanically (a direct `gh api` query against a just-uploaded artifact returned 1) and once for
real, on the master merge above. Its *negative* path — a push whose tree has genuinely no
recorded artifact, so the full suite has to run — has never happened on a real push. The
runbook (`docs/runbook/ci.md`) says so plainly and gives the two ways it will occur on its own
(7-day artifact expiry; `master` moving under a PR) and how to force it deliberately. Same
honesty for Dependabot: three real Dependabot PRs are open (#182, #183, #184) and the actor
clause has only ever been read, never exercised against an actual Dependabot event.

**The consequence worth remembering past this week:** Dependabot PRs now report green with
nothing tested, where they used to report red with nothing tested. Red was honest; green is
not, and if branch protection is ever turned on for this repo — it isn't today, GitHub Free has
none — a skipped required check counts as satisfied. `ci.yml` pins `upload-artifact@v4`, and
#183 is exactly that dependency's real upgrade, sitting behind a tick that verified nothing.
Logged to `ISSUES.md` rather than merged on the strength of the tick.

## Reflection

Two of this project's recurring lessons showed up again, smaller this time. The plan step that
could only return one answer is the "verifier is itself unverified" failure's quieter cousin —
not a check that silently passed, but a check whose own environment made the question
unanswerable, caught by reading the trigger before running anything. And the cost baseline
being one sample of a 3.5x-varying job is the same "measure it more than once before trusting
it" lesson the coverage-precision and Lighthouse-threshold work already taught this project —
just applied to wall-clock time instead of a percentage.

## 2026-09-08 — addendum: the premise was false, and I had the evidence in hand

The final whole-branch review checked the one thing I never did: **`kaleem-lms/Kaleem` is a
public repository**, and has been since it was created in 2024 (`PublicEvent` carries the same
timestamp as `created_at`). Standard GitHub-hosted runners are free on public repos. Verified
three ways: `gh api /repos/kaleem-lms/Kaleem` reports `private: false`; an unauthenticated
`curl` of the API returns 200; and `actions/runs/<id>/timing` reports
`billable.UBUNTU.total_ms: 0` for the pre-change baseline run *and* the post-change merge run,
with `run_duration_ms` populated — so the endpoint works and the answer is zero. All five
submodules are private but carry **zero workflows**, so nothing is billed anywhere either.

Everything this change was justified by — "~$62/month", "~9,700 billed minutes", "get under the
2,000-minute allowance" — is arithmetic on a bill that does not exist.

**The part worth keeping is that I saw the disconfirming evidence in the first five minutes and
explained it away.** The opening survey ran `/actions/runs/<id>/timing` across five runs, got
`total_ms: 0` every time, and I wrote it off as a broken endpoint because `gh repo view` had
just said `PRIVATE` and a `rulesets` call had 403'd with "Upgrade to GitHub Pro or make this
repository public". Two readings disagreed; I kept the one that made the task make sense and
discarded the one that did not, without spending the single command it would have taken to
settle it. I cannot now reconstruct why the first `visibility` read said `PRIVATE` — the current
answer is unambiguous and repeatable — but that uncertainty is the point: the contradiction was
visible and unresolved, and I proceeded anyway.

This is the same failure this project keeps naming, one level up again. C3b: the suite could not
represent the thing it claimed to test. C3d: the e2e passed locally under a deleted override and
could never have passed in CI. Here: the measurement was sound and the *premise under the
measurement* was never checked. Measuring carefully is not the same as measuring the right thing.

Two consequences beyond the wasted justification:

1. **A live credential exposure, pre-existing and now confirmed.** `KaleemC3d!2026` and
   `KaleemStaging!2026` were served to an anonymous `curl` from `STATE.md` on `master`. They are
   removed from the tree and stay in history. Logged under *Blocks launch* with the rotation list.
2. **ADR-0038 made `security` (gitleaks) skip on documentation-only changes** — and root-level
   `*.md` is documentation. This project's one previous leak was `portal-snapshot.md`, a
   root-level `.md`, found by the first `security` run. On a public repo that delay means
   world-readable until the next code PR. The fix now costs nothing, because minutes are free.

The docs branch `docs/ci-cost-optimization-close` is committed and deliberately **not merged**.
Merging it would publish a permanent record built on the false premise. The mechanism is sound
and stays; the justification has to be rewritten around wall-clock and noise, which are real.
