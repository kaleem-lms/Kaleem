Gates run only through `_tools/backend-gate.sh`. Every step starts with a failing test (D3),
and every regression test is mutation-checked: revert the fix and watch it go red. Floors
are not touched (dec-floor-ownership). The owner answered `D-ntf-channels` (email, in-app

services, and no sender.

Each step lists its files under `backend/kaleem/notifications/` unless it says otherwise.
Tests go in `tests/`.

## Risks

- **`ntf-email-foundation` builds against the interface in parallel, in wave 3.** The spec
  pins the `Protocol` and both delivery services, so either unit can merge first. If
  email-foundation merges first, it carries no channel until this unit lands.
- **Transitive contracts.** `ana-scheduling-read-api` and any later edge from a
  non-producer into a producer would break that module's contract once scheduling imports
  `notifications.services`. The ADR's ignore rule covers this, and the reviewer checks it.
- **Unread items purged at 90 days.** This is accepted under `dec-retention-new-domains`
  and stated in `notifications.md`.
- **`get_or_create` under fan-out is O(n) queries.** v1 fan-outs are in the tens, and the
  query-count test bounds the growth.
- **Open decisions.** If the owner answers the two `D-ntf` decisions differently, the
  structure still holds (spec). Only the adapters that exist and the producers' flags
  change.
