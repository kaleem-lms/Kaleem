## Risks

- **zod precedence.** A schema-level `message` silently bypasses the map. Covered by the
  step 2 precedence test and the step 3 `schemas.ts` scan. A message written inline in a
  component's local schema (outside `schemas.ts`) is not caught by the scan; review checks it.
- **Two zod copies.** If the resolver resolved a different zod instance, the global config
  would not reach it. One `zod@4.3.6` is in the lockfile today; step 5's form tests go
  through the real resolver, so a split would show red there.
- **Entry chunk growth.** Importing `@/lib/zod` from any entry module would pull zod into
  the initial JS. Step 7 measures it; fallback is to move the offending import, not to raise
  the budget.
- **Namespace not yet loaded** when a form validates (root loader still in flight, or the
  JSON failed): the message falls back to zod's English. The root loader is awaited before
  any route renders, so only a failed download reaches this; accepted and stated in the spec.
- **Arabic digits in jsdom.** Node's ICU may format Arabic numbers differently from Chrome;
  every digit assertion computes its expectation with `Intl` in the same runtime, never a
  literal.
- **Arabic copy and plural forms** need owner review (`hg-arabic-review`, batched per wave);
  it holds spec closure, not the merge.
